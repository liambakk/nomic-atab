# Working in this repository

Ben is Liam's point of contact. Atab's technical contributors can edit the files here, while the business reviewer can provide answers through a walkthrough or written notes. Liam can enter those answers and record who confirmed them.

## Without Git

Read the brief, complete the relevant templates in your preferred editor and send them with the private source folder to Liam. Use the same case references as the file index. Liam can update this repository from the handoff.

## In the browser

With repository write access, open the file to change and use its edit control. Describe the change when saving. For a change that needs discussion, propose it on a new branch and open a pull request for Liam to review. Use the issue forms for missing information or a case ready for review.

## What to include in a change

- Explain what changed and which workflow, case or rule it affects.
- Reference the source file and location, or name the reviewer and review date.
- Distinguish documented facts, recollections, proposals and confirmed corrections.
- Keep raw exports in the private source folder. Include only material cleared for the people with repository access.
- Update the manifest if a source file or its version changes.
- Record reusable confirmed answers in the decision log and relevant notes.

For missing information, identify whether it is not recorded, needs collecting, needs explanation or has permission pending. Name the person who can help where known. Avoid guessing a deadline or claiming a task is accepted until the relevant person has agreed.

## Maintaining the brief

Edit [brief.md](brief.md) for wording changes, then follow [document maintenance](docs/maintenance.md) to refresh the Word copy. Keep the Word document in Helvetica, 11-point black text, with only the document title and main section headings bold. Markdown display follows GitHub's own styles.
